# 技术决策说明：库选型与自研边界

## 目标

为 `flutter-gradle-tool` 确定最小且可维护的技术栈，避免为单用途 CLI 引入过重依赖，同时保证后续实现成本可控。

## 结论

| 领域 | 决策 | 原因 |
|------|------|------|
| CLI 框架 | 使用 `cobra` | 子命令、flags、help 和错误处理都能明显减少重复代码 |
| 项目配置 | 自己实现 | `.fgt-config` 仅需少量字段，`encoding/json` 足够 |
| 交互选择 | 先自写简单菜单，必要时再引入 `promptui` | 当前镜像源数量少，简单选择器工作量更低 |
| 富交互界面 | 不使用 `bubbletea` | 需求不复杂，TUI 框架会放大实现和维护成本 |
| 日志 | 先用标准库 `log` 或 `log/slog` | 轻量、依赖少，满足 CLI 场景 |
| HTTP 请求 | 标准库 `net/http` | 镜像测速和探测不需要额外封装 |
| 进程执行 | 标准库 `os/exec` | `exec` 命令只需要调用 Gradle wrapper |

## 选择依据

### 1. `cobra`

- 适合树状命令结构：`fgt mirror list`、`fgt mirror set`、`fgt init`、`fgt doctor`。
- 提供成熟的 flags、help、usage 和命令路由支持。
- 能减少手工维护命令解析和帮助文案的成本。

### 2. `.fgt-config` 自研

- 当前只需要保存当前镜像源名称，JSON 文件就足够。
- 自研能保持文件格式稳定，后续扩展字段也容易。
- 不需要 `Viper` 提供的多来源配置、环境变量映射、远程配置等能力。

### 3. 交互选择自写

- 当前内置镜像源只有 4 个，简单列表即可覆盖大多数场景。
- 自写菜单能更直接地控制确认流程、错误提示和行为幂等性。
- 如果后续加入测速结果、搜索过滤或更复杂展示，再引入 `promptui` 更合适。

### 4. 不使用 `bubbletea`

- 本项目不是长期运行的终端应用，也不需要复杂布局或实时状态面板。
- 引入 TUI 框架会增加状态管理、渲染和测试成本。
- 在当前规模下收益不明显。

## 推荐实现边界

- `cobra` 负责命令树和参数解析。
- 标准库负责配置、HTTP、文件系统和进程执行。
- `.fgt-config` 保持 JSON 格式，字段最少化。
- 交互式选择保持轻量，先满足可用性，再考虑增强依赖。

## 依赖原则

1. 先满足核心功能，再考虑体验增强。
2. 能用标准库解决的，不引入第三方库。
3. 只有当依赖显著减少代码量、测试量或错误面时，才引入新库。
4. 所有新增依赖都应能在 `docs/` 中找到对应理由。
